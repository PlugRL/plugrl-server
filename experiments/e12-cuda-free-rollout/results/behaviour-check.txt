E12 behaviour check - does the CUDA-free env client behave like the other one?
Cluster qz103, 2026-09-18. Server unchanged throughout: pi0-policy, pi05_libero,
eval algorithm, CUDA, GPU 0. Only the client's Python differs.

Harness: verify_cpu_client.sh, libero_spatial task 0, 3 episodes, initial states
in order, seed 7, replan-steps 5, one env, one process.


THE CHECK AS THE PROTOCOL WROTE IT: FAILED
------------------------------------------
PROTOCOL.md required successes and step counts to match an existing run
exactly: 3 of 3, 301 env steps, 61 inference calls, 61 feedback calls.

  run                         client  success  env_steps  infer  feedback
  demo capture (2026-09-18)   CUDA    3/3      301        61     61
  cpu-verify                  CPU     3/3      296        60     60

296 is not 301. Prediction 4 is falsified as written.


WHY, AND WHAT THE CONTROL SHOWS
-------------------------------
The premise was wrong, not the client. The protocol assumed the run is
deterministic because the environment is seeded. The policy is not seeded:
openpi_policy.py:119 draws fresh noise for every inference,

    x = torch.randn(batch_size, self.action_horizon, self.action_dim, ...)

and nothing in src/plugrl_server calls manual_seed, np.random.seed or
torch.use_deterministic_algorithms - a search over the whole package returns
no matches. Two runs of the same configuration therefore take different
trajectories.

A control run, the CUDA client through the same harness, confirms it:

  run                         client  success  env_steps  infer  feedback
  demo capture (2026-09-18)   CUDA    3/3      301        61     61
  cuda-control                CUDA    3/3      300        61     61
  cpu-verify                  CPU     3/3      296        60     60

CUDA against CUDA already differs. The exact-match check could not have passed
for any client, including the unmodified one.


THE CHECK THAT ISOLATES THE CLIENT: PASSED
------------------------------------------
Designed after the failure above, and labelled as such.

An episode's first observation depends on the initial state, which is fixed and
taken in order, and not on anything the policy did. If the CUDA-free client
sees and sends the same frames, it is behaving identically at the only place it
can be compared free of the policy's randomness.

WHAT THIS DOES NOT SHOW
-----------------------
- Not that success rates are equal. Three episodes on one task, all successful
  in both, says nothing about the rate on a suite.
- Not that every environment behaves this way. One task of libero_spatial.
- Not that the runs are otherwise identical: the step counts differ, and with
  an unseeded policy there is no configuration under which they would not.
